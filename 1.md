For freshers, I recommend teaching **System Management as a troubleshooting story**, not as a list of commands. Start with the payment-app scenario you just created, then gradually introduce each command as a tool to investigate the problem.

# Linux System Management — Teaching Flow

## 1. Start with the Real-World Scenario

Tell students:

> **"Imagine we support a payment application. Users are reporting that the application is very slow, and some users cannot complete their payments."**

Show the architecture:

```text
Customer
   ↓
Web/API Server
   ↓
Application Server
   ↓
Database Server
```

Then ask:

> **"As a Linux Support Engineer, where do we start?"**

Don't immediately give them commands.

Tell them:

> "We first need to understand whether the Linux server itself is healthy."

---

# 2. Introduce the Troubleshooting Flow

Write this on the board:

```text
USER REPORT
    ↓
CHECK SERVER
    ↓
CHECK SYSTEM HEALTH
    ↓
CHECK RESOURCES
    ↓
CHECK PROCESSES
    ↓
CHECK SERVICES
    ↓
CHECK LOGS
    ↓
IDENTIFY PROBLEM
    ↓
FIX PROBLEM
    ↓
VERIFY
```

Tell students:

> **"This is our System Management troubleshooting approach."**

---

# 3. Step 1 — Identify the Server

### Question

> "First, which server are we connected to?"

Run:

```bash
hostname
```

Then:

```bash
hostnamectl
```

Explain:

```text
hostname
    ↓
Tells us server name

hostnamectl
    ↓
Gives detailed system information
```

Also:

```bash
whoami
```

Explain:

> "Before troubleshooting, always know **which server** and **which user** you are working with."

---

# 4. Step 2 — Check Operating System

Run:

```bash
cat /etc/os-release
```

Then:

```bash
uname -a
```

Explain:

```text
/etc/os-release
        ↓
OS information

uname -a
        ↓
Kernel/system information
```

For example:

```text
Ubuntu
Linux kernel
x86_64 architecture
```

---

# 5. Step 3 — Check Server Uptime

Ask:

> "Is the server running normally, or was it recently restarted?"

Run:

```bash
uptime
```

Example:

```text
up 15 days, 4 hours
```

Explain:

> "`uptime` tells us how long the server has been running and also gives us the system load."

At this stage introduce **load average** only briefly.

Don't go deep into it for freshers.

---

# 6. Step 4 — Check CPU

Now return to the problem:

> **"Users say the payment application is slow. Could the server CPU be overloaded?"**

Run:

```bash
top
```

Tell students to observe:

```text
CPU usage
Memory usage
Load
Running processes
```

Exit:

```text
q
```

### Simple explanation

> **CPU is the processing power of the server. If a process consumes excessive CPU, applications may become slow.**

---

# 7. Step 5 — Check Memory

Ask:

> "Could the server be running out of memory?"

Run:

```bash
free -h
```

Explain:

```text
total
used
free
available
swap
```

For freshers, emphasize:

> **Always look at `available` memory rather than assuming that all memory shown as `used` is a problem.**

Keep the explanation simple.

---

# 8. Step 6 — Check Disk

Ask:

> "What happens if the server's disk becomes full?"

Run:

```bash
df -h
```

Example:

```text
Filesystem      Size  Used Avail Use%
/dev/root        30G   29G   1G   97%
```

Explain:

> "If the filesystem becomes full, applications may fail to write logs, temporary files, or application data."

This is a very important production troubleshooting check.

---

# 9. Step 7 — Find What Is Consuming Resources

Now introduce processes.

Run:

```bash
ps aux
```

Explain:

> **A process is a running program.**

For example:

```text
nginx
java
mysql
sshd
```

To find Java:

```bash
ps aux | grep java
```

To find Nginx:

```bash
ps aux | grep nginx
```

Connect it to the scenario:

```text
Payment Application
       ↓
Java process
       ↓
Check whether Java is running
```

---

# 10. Step 8 — Introduce Services

Now tell students:

> "A process can run as part of a service. Linux provides `systemctl` to manage many services."

For example, Nginx:

```bash
sudo systemctl status nginx
```

Students should understand:

```text
systemctl status
        ↓
Is the service running?
```

---

# 11. Step 9 — Create a Problem Yourself

This is where the class becomes **hands-on**.

First make sure Nginx is running:

```bash
sudo systemctl start nginx
```

Check:

```bash
sudo systemctl status nginx
```

Then intentionally create the problem:

```bash
sudo systemctl stop nginx
```

Now tell students:

> **"Users are reporting that the website is not working. Find the problem."**

Don't tell them the answer.

---

# 12. Step 10 — Students Troubleshoot

Let them follow the flow:

### Check server

```bash
hostname
```

### Check uptime

```bash
uptime
```

### Check CPU

```bash
top
```

### Check memory

```bash
free -h
```

### Check disk

```bash
df -h
```

### Check processes

```bash
ps aux
```

### Check Nginx

```bash
sudo systemctl status nginx
```

Eventually they should discover:

```text
Active: inactive (dead)
```

---

# 13. Step 11 — Fix the Problem

Ask:

> "What should we do?"

Start the service:

```bash
sudo systemctl start nginx
```

Verify:

```bash
sudo systemctl status nginx
```

Expected:

```text
Active: active (running)
```

---

# 14. Step 12 — Test the Application

Don't stop at `systemctl`.

Test the application:

```bash
curl http://localhost
```

If Nginx is working, you should receive an HTTP response.

Explain:

> **"A service showing `active` does not automatically prove that the application is working correctly. We should test it."**

---

# 15. Step 13 — Check Logs

Once students understand services, introduce logs.

For Nginx:

```bash
sudo journalctl -u nginx
```

You can also show:

```bash
sudo journalctl -u nginx --since "30 minutes ago"
```

Explain:

> "When a service fails, logs can tell us what happened."

Don't go deeply into `journalctl` initially.

---

# 16. Step 14 — Service Management Commands

Now that students understand the concept, teach these commands together:

### Start

```bash
sudo systemctl start nginx
```

### Stop

```bash
sudo systemctl stop nginx
```

### Restart

```bash
sudo systemctl restart nginx
```

### Status

```bash
sudo systemctl status nginx
```

### Enable at boot

```bash
sudo systemctl enable nginx
```

### Disable at boot

```bash
sudo systemctl disable nginx
```

### Check whether enabled

```bash
sudo systemctl is-enabled nginx
```

---

# 17. Explain `start` vs `enable`

This is an important concept.

```text
systemctl start nginx
        ↓
Start nginx NOW
```

Whereas:

```text
systemctl enable nginx
        ↓
Start nginx automatically when
the server boots
```

For example:

```text
Server reboot
     ↓
Linux starts
     ↓
Nginx automatically starts
```

---

# 18. Step 15 — Reboot Management

Finally introduce:

```bash
sudo reboot
```

Explain:

> "A reboot is a system-level operation. In production, we don't randomly reboot servers."

Before rebooting a production server, engineers generally consider:

```text
Maintenance window
      ↓
Impact on users
      ↓
Application availability
      ↓
Approval/change process
      ↓
Reboot
      ↓
Verify services
```

# 20. What Students Should Learn

Don't teach 30 commands in one class.

For the **first System Management class**, focus on these:

| Area             | Command               |
| ---------------- | --------------------- |
| Current user     | `whoami`              |
| Server name      | `hostname`            |
| OS               | `cat /etc/os-release` |
| Kernel           | `uname -a`            |
| Uptime           | `uptime`              |
| CPU/processes    | `top`                 |
| Memory           | `free -h`             |
| Disk             | `df -h`               |
| Processes        | `ps aux`              |
| Service status   | `systemctl status`    |
| Start service    | `systemctl start`     |
| Stop service     | `systemctl stop`      |
| Restart service  | `systemctl restart`   |
| Logs             | `journalctl`          |
| Test application | `curl`                |

### The key message for students

> **"System Management is not about memorizing Linux commands. It is about knowing what to check when a server or application has a problem."**

That mindset will also prepare them for the **Linux troubleshooting questions they will encounter in DevOps interviews**.
